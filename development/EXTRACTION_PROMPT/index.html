    MCscan3 Extraction and Rebranding: AI Coding-Agent Prompt¶

    How to use. Paste everything below the line into an agentic coding tool (for example Claude Code) opened in an empty folder on your Mac. The agent downloads JCVI itself. It works in phases and stops after each one for your review; reply "continue" to go on. This prompt is a more detailed replacement for Phases 0 to 3 of the earlier MCscan3_agent_prompt.md.

    ROLE AND GOAL¶

    You are a senior bioinformatics software engineer. Build MCscan3, a standalone, rebranded Python package containing every MCscan-related feature of JCVI, with each feature implemented as its own separate module, command, test file and documentation page.

    MCscan3 is the official successor to MCScan (2008), JCVI's Python MCscan, and MCScanX (2012). The original authors, Haibao Tang and Yupeng Wang, are on the team and will review the code.

    Success means: 1. pip install . works on a clean machine with no jcvi package installed. 2. Every JCVI MCscan feature listed in the Feature Map below exists as a separate MCscan3 feature. 3. Every feature produces the same results as JCVI on the test data (parity tests). 4. The branding is consistent everywhere, while JCVI and the original authors are properly credited.

    NON-NEGOTIABLE RULES¶

    • Parity first. Ported features must reproduce JCVI outputs exactly. If you find a bug in JCVI, keep the original behaviour as the default, add an opt-in flag for the fix, and record it in docs/DEVIATIONS.md.
    • Attribution. JCVI is BSD-licensed. Keep its copyright notice in LICENSE-THIRD-PARTY, and put a header in every derived file: # Derived from JCVI <original path> (BSD license), commit <hash>.
    • Only JCVI code. Do not copy code from any other tool in this task.
    • One feature at a time. Port, test and commit each feature separately. Never leave the test suite failing at a commit.
    • Stop at every checkpoint with a short report: what was done, test results, problems, and open questions. Ask instead of guessing on design decisions not covered here.
    • Python 3.10+, type hints on public functions, docstrings, ruff and mypy clean, pytest for tests.

    BRANDING SPECIFICATION¶

    Item Value
    Product name MCscan3 (always this capitalization in text)
    PyPI / import name mcscan3
    Command-line tool mcscan3
    Starting version 0.1.0.dev0 (single source of truth in src/mcscan3/__about__.py)
    Tagline "Synteny, whole-genome duplication and genome evolution analysis"
    License BSD-3-Clause for new code; JCVI notice kept in LICENSE-THIRD-PARTY
    Credits line "MCscan3 builds on MCScan and JCVI (Haibao Tang) and MCScanX (Yupeng Wang)."

    Branding must appear in all of these places: - mcscan3 --version prints the name, version, tagline, credits line, and "Cite: run mcscan3 cite". - mcscan3 cite prints citations for MCScan (Tang et al. 2008), MCScanX (Wang et al. 2012) and JCVI (Tang et al. 2024, iMeta), plus MCscan3 once published. Also provide CITATION.cff. - Log messages use the logger name mcscan3 with a consistent format. - Every figure saved by MCscan3 records Creator: MCscan3 <version> in its file metadata (PDF and PNG metadata, SVG comment). No visible watermark. - A shared visual theme module (mcscan3.plot.theme) with default fonts and palettes, including a colour-blind-safe palette. - README.md with a logo placeholder (docs/assets/logo.svg, a simple original text-based design; do not use any existing logos). - A documentation site (MkDocs Material) titled "MCscan3".

    After branding is complete, the command grep -rni "jcvi" src/ must return only attribution headers and the legacy alias layer described below.

    "EACH FEATURE SEPARATELY": REQUIRED STRUCTURE¶

    Every feature gets: 1. Its own module under src/mcscan3/features/<group>/<feature>.py containing a pure Python API function (data in, data out, no printing, no argument parsing). 2. Its own CLI command mcscan3 <group> <feature>, a thin wrapper around the API function. 3. Its own entry in a feature registry (src/mcscan3/registry.py) with: name, group, one-line description, JCVI source (module and action), status (ported, parity-verified, legacy-only), and the test file name. 4. Its own test file tests/features/test_<group>_<feature>.py with at least one parity test against JCVI output. 5. Its own documentation page docs/features/<group>/<feature>.md with purpose, inputs, outputs, options, an example command, and its JCVI equivalent.

    Add these supporting commands: - mcscan3 features lists all features from the registry as a table (group, command, status, JCVI equivalent). - mcscan3 legacy <jcvi.module> <action> ... maps old JCVI command lines to the new commands, so python -m jcvi.compara.catalog ortholog grape peach becomes mcscan3 legacy compara.catalog ortholog grape peach. It prints a one-line hint with the new command name.

    Shared code (file readers and writers, geometry, the union-find Grouper, LIS, range utilities) goes in src/mcscan3/core/ and src/mcscan3/io/, not inside feature modules.

    FEATURE MAP (JCVI source → MCscan3 feature)¶

    Verify this map against the JCVI source in Phase 0 (it was built by reading each module's actions list). Add anything missing, and mark anything that is project-specific.

    Group prep: input preparation¶

    MCscan3 command JCVI source
    prep gff2bed formats.gff bed (including --type=mRNA --key=Name and longest-isoform options)
    prep fasta-format formats.fasta format (ID cleanup used in the MCscan tutorial)

    prep bed-uniq formats.bed uniq

    Group align: homology search¶

    align last apps.align last (the default aligner used by catalog ortholog)
    align blast apps.align blast

    Group filter: hit filtering¶

    filter blastfilter compara.blastfilter main (tandem removal, C-score, repeat filter)
    filter cscore formats.blast cscore
    filter best formats.blast best
    filter rbbh formats.blast rbbh

    Everything else in JCVI (assembly, annotation, variation, projects, most format tools) is out of scope.

    PHASE 0: DOWNLOAD, INVENTORY AND GOLDEN OUTPUTS¶

    1. On macOS, check prerequisites and report what is missing: Xcode command line tools, Homebrew, uv (or Python 3.10+), git, and the LAST aligner (brew install last if available, otherwise conda/bioconda). Do not install system software without asking.
    2. Clone JCVI: git clone https://github.com/tanghaibao/jcvi.git vendor/jcvi, check out the latest release tag, and record the tag and commit hash in docs/SOURCE_VERSION.md. Add vendor/ to .gitignore; it is reference material only and must never be imported by mcscan3.
    3. Install that JCVI version into a separate virtual environment (.venv-jcvi) to produce golden outputs. MCscan3's own environment must not contain jcvi.
    4. Write tools/inventory.py that parses every in-scope JCVI module, extracts its actions tuple (or single main), and prints the list. Compare with the Feature Map above and report differences.
    5. Map the internal import graph of all in-scope modules, including transitive imports. In docs/EXTRACTION_PLAN.md, record for each dependency whether it will be ported into core/ or io/, replaced with a standard library (for example Biopython, pyfaidx, natsort), or dropped. Note especially: apps.base (option parsing, sh, logging), formats/cblast.pyx (Cython), formats.blast importing assembly.base, apps.r (R dependency), and algorithms.lpsolve (SCIP/GLPK).
    6. Build test data: the grape and peach example from the JCVI MCscan tutorial, reduced to a few chromosomes so the full test suite runs in under two minutes. Add one small polyploid-versus-diploid pair to exercise quota ratios such as 1:2.
    7. Run the original JCVI on the test data for every feature in the Feature Map and save outputs in tests/golden/<group>/<feature>/, together with the exact command used. Figures: save PNG at fixed DPI plus SVG. Write tools/make_golden.sh to regenerate everything.

    Checkpoint 0: inventory differences, extraction plan, test data description, and the list of golden outputs (with any features that could not be run and why).

    PHASE 1: SKELETON AND BRANDING¶

    1. Create the package layout, pyproject.toml, the Typer CLI with one sub-app per group, the registry, mcscan3 --version, mcscan3 cite, mcscan3 features, the theme module, figure metadata, logging, CITATION.cff, README, license files, and the MkDocs skeleton.
    2. Set up GitHub Actions: ruff, mypy, pytest on macOS and Linux, Python 3.10 to 3.12.
    3. Add a test that fails if any registered feature is missing its module, CLI command, test file or documentation page.

    Checkpoint 1: output of mcscan3 --version, mcscan3 features (all features listed as not-ported so far), and CI status.

    PHASE 2: SHARED CORE AND FILE FORMATS¶

    1. Port the shared pieces into core/ and io/: Grouper, LIS functions, range utilities, BED reader (Bed, BedLine, order, order_in_chr), BLAST reader (replace the Cython cblast with pure Python or Polars unless it is more than 3x slower on the test data), anchors/simple/blocks/layout/seqids readers and writers, sizes, and the quota integer-programming wrapper (support SCIP and GLPK as JCVI does; add HiGHS as an optional solver).
    2. Unit tests for each reader and writer, including round trips.

    Checkpoint 2: coverage report for core/ and io/.

    PHASE 3: PORT FEATURES ONE BY ONE¶

    Port in this order, because later features depend on earlier ones: prep → align → filter → synteny scan/liftover/screen/simple/summary/stats/depth → quota → ortholog run (must reproduce the full tutorial pipeline) → remaining synteny features → ortholog catalog features → ks → fractionation → ancestral, pad, synfind → phylo.

    For each feature: 1. Write the pure API function, then the CLI wrapper, registry entry, documentation page and parity test. 2. Parity means byte-identical text output compared with the golden file. If JCVI's output order is not deterministic, sort both sides and document it in the test. 3. Commit with the message feat(<group>): port <feature> from jcvi <module>.<action>. 4. Update the feature's registry status to parity-verified only when its parity test passes.

    Checkpoint 3a after ortholog run works end to end, and Checkpoint 3b after all analysis groups: parity table (feature, golden file, pass/fail), deviations, and runtime compared with JCVI.

    PHASE 4: PORT ALL GRAPHICS¶

    1. Port graphics/base.py and glyph.py into mcscan3.plot, applying the MCscan3 theme without changing default JCVI-looking output unless the user passes --theme mcscan3. Default to the JCVI look for parity.
    2. Port each plot feature separately, following the same five-part structure (module, command, registry, test, docs page).
    3. Test figures with image comparison against the golden PNGs (for example pytest-mpl with a small tolerance), and check that figure metadata contains Creator: MCscan3.
    4. Add mcscan3 plot gallery, which renders every plot from the test data into one HTML page for team review.

    Checkpoint 4: the gallery and the image-comparison results.

    PHASE 5: LEGACY ALIASES, DOCUMENTATION AND FINAL VERIFICATION¶

    1. Implement mcscan3 legacy for every ported JCVI action and test that the JCVI MCscan tutorial runs unchanged except for the prefix.
    2. Write docs/MIGRATION_FROM_JCVI.md: a table of every JCVI command and its MCscan3 equivalent, generated from the registry.
    3. Write a quick-start tutorial reproducing the grape-peach MCscan tutorial with the new commands.
    4. Final checks, reported in the last checkpoint:
    5. pip install . in a fresh environment without jcvi, then run the full test suite.
    6. grep -rni "jcvi" src/ returns only attribution headers and the legacy layer.
    7. python -c "import mcscan3" does not import jcvi (check sys.modules).
    8. Every registry entry has status parity-verified or legacy-only with a written reason.
    9. Build the documentation site without warnings.

    Final checkpoint: a release summary suitable for Haibao Tang and Yupeng Wang to review, listing every feature, its status, and any deviations.

    OUT OF SCOPE¶

    New analysis algorithms (Orthology Index, WGD peak fitting, subgenome phasing, networks, pangenomes), the MCScanX C++ engine port, and new plot types. Those are later tasks defined in the MCscan3 Feature Catalog. This task delivers a complete, rebranded, parity-verified MCscan core that they will build on.

    MCscan3 builds on MCScan and JCVI (Haibao Tang) and MCScanX (Yupeng Wang). BSD-3-Clause.
