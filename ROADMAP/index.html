    MCscan3 roadmap: Phase 6 (after the JCVI extraction is complete)¶

    Status (2026-09-29): all seven items are implemented, tested and documented. Their registry status is new. The commands are listed in the table below, and the migration guide has a "New in MCscan3" section. The open questions were settled as follows, following the owner's instruction to proceed with defaults:

    • Gene trees: wgd tree-map takes gene trees as input (Newick files). MCscan3 does not build them, so IQ-TREE, MAFFT and OrthoFinder are not dependencies. Rooting (minimum duplication), reconciliation and counting are built in.
    • Pan-genes: pan genes uses MCscan3's own synteny (the anchors of ortholog run), not OrthoFinder.
    • Networks: Infomap, used in the original network studies, is replaced by MCL (built in) or Louvain (networkx).
    • Maximum-likelihood trees: network profile --phylip writes the binary matrix for RAxML or IQ-TREE. The built-in trees are NJ or UPGMA.

    Requested by the project owner on 2026-09-28. These start only after Phases 0–5 of docs/development/EXTRACTION_PROMPT.md are finished and signed off. They are new features, so they follow the same five-part structure (module, CLI command, registry entry, tests, docs page), but their registry status is new and they have no JCVI parity tests. Instead they get correctness tests on synthetic data and, where possible, comparisons against the published tool's outputs.

    Clean-room rule: the extraction task forbids copying code from tools other than JCVI. The features below are re-implementations of the published methods (from the papers), cite the original tools, and must not copy their source code. Several of those tools are GPL-licensed, which is incompatible with MCscan3's BSD-3 license.

    # Feature Proposed group / commands Method reference (to cite)
    6.1 Raw genome GFF3 + FASTA → longest-isoform BED/CDS/PEP in one step (done) prep genome JCVI formats.gff bed / load behaviour; new --longest option
    6.2 Duplicate-gene classification (WGD, tandem, proximal, transposed, dispersed, singleton) (done) dup classify DupGen_finder (Qiao et al. 2019, Genome Biology)
    6.3 Synteny-based ortholog filtering using the Orthology Index (SOI) (done) ortholog soi SOI (Zhang et al. 2024/2025)
    6.4 Genome-wide Ks distributions and WGD inference (paranome, anchor Ks, mixture models, peak calling, Ks correction) (done) wgd ksd, wgd peaks, wgd mix, wgd correct wgd v2 (Chen, Zwaenepoel et al. 2024, Bioinformatics)
    6.5 WGD placement on a species tree from gene trees (done) wgd tree-map Tree2GD (Chen et al. 2023)
    6.6 Pan-gene / pan-synteny analysis across many genomes (synteny-constrained orthogroups, riparian plots) (done) pan genes, plot riparian GENESPACE (Lovell et al. 2022, eLife)
    6.7 Multi-species synteny network, clustering, and phylogenomic profiling / tree building from the network (done) network build, network cluster, network profile, network tree Zhao & Schranz 2017/2019, PNAS

    Note: the extraction prompt lists "Orthology Index, WGD peak fitting, … networks, pangenomes" as out of scope for the extraction task and defers them to the MCscan3 Feature Catalog. This roadmap records the owner's request so they are scheduled right after it.

    The open questions (gene-tree dependencies, and OrthoFinder or MCscan3's own clustering for pan-genes) were settled as described at the top of this page.

    Phase 7: comparative-genomics suite (requested 2026-09-30 to 2026-10-04)¶

    Same rules as Phase 6: new features are clean-room reimplementations from the papers (the tools named below are inspiration and are cited, their code is never copied), each with a module, CLI command, registry entry (new, with a method), tests on synthetic data with a known answer, validation on real genomes, and a docs page. "Full pipelines, not stubs" (owner, 2026-10-04).

    Done:

    Feature Commands
    End-to-end pipeline from a directory of genomes, with HTML report pipeline inputs, pipeline run
    Robust Ks modelling (GMM, ELMM, BGMM, bootstrap CIs, block Ks, codeml Ks) wgd mix, wgd blocks, wgd ksd --method codeml
    Ancestral gene orders at every node, ancestral chromosomes painted WGDI/AKRUP-style ancestral genomes, ancestral karyotype
    Readable dot plots, karyotypes and riparian plots on real genomes plot dotplot/karyotype/riparian (--theme mcscan3)
    Biased fractionation and progenitor-based subgenome assignment, validated on B. rapa, maize and B. napus (7.1) subgenome fractionation, subgenome assign

    WGDs on the species tree by consensus of block ratio, quota ratio, rate-corrected Ks and gene-tree bursts; validated on six eudicots (gamma, alpha/beta, salicoid, both soybean WGDs; no false calls) wgd consensus, pipeline step wgd-consensus, ancestral tree-karyotype --wgd

    What goes wrong with EDTA, and what MCscan3 does instead (owner request 2026-10-26)¶

    Moved ahead of Phase 10 on 2026-10-26 ("take EDTA, see what's wrong with it and not fast, integrate new tools and features, make it a world-class detailed repeat annotation, with TEsorter-like things"). From the EDTA README and issue tracker (about 600 closed issues):

    Problem with EDTA MCscan3 te
    About 20 external programs (TIR-Learner with a deep-learning model, HelitronScanner in Java, RepeatModeler, AnnoSINE, LTR_FINDER, LTRharvest, LTR_retriever, RepeatMasker, cd-hit, mdust...); versions break each other (pandas 2, TIR-Learner 4, containers) native discovery of every order (C kernels with pure-Python fallbacks); only HMMER and BLAST/minimap2 needed; external finders optional, as extra evidence
    Slow steps: TIR-Learner and RepeatModeler run for days on large genomes; whole-genome RepeatMasker k-mer seeded search per chromosome in parallel; library masking split by chromosome; every step cached and resumable
    Fragile input: sequence names of 13-15 characters at most, failures on large single chromosomes, empty-file and "not found" crashes, silent "no SINE found" stops names mapped internally; any size; every step writes its result (even empty) and the run report says what each step found
    Inconsistent outputs (intact FASTA, GFF3 and library disagree; superfamily labels lost on reruns) one table of elements from which GFF3, FASTA, library and figures are all written
    Many "unknown" LTR elements; classification only to superfamily (TEsorter optional) REXdb domain classification to clade built in (Ty1/copia and Ty3/gypsy clades, LINE clades, TIR transposases), with domain order and completeness
    Helitron false positives; gene fragments in the library hairpin and end-motif scoring for Helitrons; protein-domain and CDS filters for gene fragments; tandem-repeat filter
    Little analysis after annotation insertion times (K2P, per clade), solo:intact ratios, LAI along chromosomes, Kimura landscapes, density along chromosomes, TE-gene distances, TEs near SVs and in synteny gaps, benchmark against curated libraries

    Commands (mcscan3 te ...): ltr, tir, helitron, nonltr (LINE/SINE), tandem, classify, library, annotate (homology masking, fragments, Kimura divergence), age, lai, landscape (figures), bench (against a curated library: sensitivity, specificity, precision, F1 per superfamily and a confusion matrix), and run (all of them, resumable).

    Build order: 11.1 LTR (kernel, intact elements, TSD/motif/PBS/PPT, identity and age) -> 11.3 REXdb classification -> 11.1 TIR/MITE, Helitron, LINE/SINE, tandem -> 11.2 library and genome annotation -> 11.4 ages, LAI, landscapes -> te run and te bench -> 11.5 phasing.

    First head-to-head (2026-10-26, simulated 3.9 Mb genome with 80 intact LTR elements, 8 nested, solo LTRs, truncated copies, tandem duplications and satellites): te ltr found 80/80 with exact boundaries and no false calls in 3 s (4 CPUs); EDTA's LTR module (LTRharvest + LTR_FINDER_parallel + LTR_retriever, 4 CPUs, osx-64 build) found 45/80, no false calls, in 441 s. It missed all 11 elements below 92% LTR identity, 9 of 12 hosts broken by later insertions and 4 of 8 nested ones.
